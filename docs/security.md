# 명령 콘솔 보안 정리

> 대시보드 명령 콘솔(`/api/exec`)을 root 권한으로 운영할 때의 보안 이슈와 완화 방법 정리.
> 관련 코드: `bridge.py` (명령 실행), `dashboard_html/` (콘솔 UI)

---

## 배경: 콘솔은 왜 root가 필요한가

실습 스크립트들은 무선 인터페이스·모니터 모드·hostapd 등을 다루므로 **root 권한**이 필요하다.

| 명령 | root 필요 | 비고 |
|------|:--------:|------|
| `bash et_check_deps.sh` | ✅ | 도구 점검/설치 |
| `bash et_scan.sh` | ✅ | AP 스캔(모니터 모드) |
| `python3 detector/et_detector.py` | ✅ | pcap 분석(root 소유 캡처 접근) |
| `bash lab_victim_ap.sh` | ✅ | 피해 AP(백그라운드) |
| `bash et_sniffing_attack.sh` | ✅ | 가짜 AP+deauth+스니퍼(백그라운드) |
| `iw dev` / `iwconfig` / `cat et_config.conf` | ❌ | 조회용 |

### bridge의 자동 sudo 처리 (`bridge.py`)
- root가 필요한 항목에는 `"root": True` 표시.
- 실행 시:
  - bridge가 **root면** → 그대로 실행(sudo 없음)
  - bridge가 **일반 사용자면** → 앞에 `sudo -n` 자동 부착
  - 사용자가 `sudo`를 직접 입력해도 **중복 없이** 정리
- 즉 **대시보드에서 `sudo`를 칠 필요가 없다.** `bash et_scan.sh`만 입력하면 된다.
- `WFSAT_SUDO=""` 로 자동 sudo 비활성화 가능.

---

## 운영 방식 두 가지

### 방식 A — bridge를 root로 실행 (실습 랩에서 가장 간단)
```bash
sudo WFSAT_HOST=127.0.0.1 python3 bridge.py
```
- 서버 시작 시 **한 번만** 비밀번호 입력. 이후 sudo·비밀번호 불필요.
- 시작 로그에 `Privilege : running as root` 표시.

### 방식 B — 특정 명령만 NOPASSWD sudoers (권한 최소화 지향)
```bash
sudo visudo -f /etc/sudoers.d/wfsat
```
```
kali ALL=(root) NOPASSWD: /usr/bin/bash, /usr/bin/python3, /usr/sbin/iw, /usr/sbin/iwconfig
```
- 이후 일반 사용자로 `python3 bridge.py` 실행 → `sudo -n`이 비밀번호 없이 통과.
- ⚠️ **한계**: `bash`/`python3`를 NOPASSWD로 열면 "임의 인자 허용"이라 사실상 root 전체 권한과 큰 차이가 없다. 스크립트가 내부적으로 다양한 root 도구를 호출하므로 스크립트 하나만 딱 잠그기는 어렵다. → **일회용 격리 VM이라면 방식 A가 더 깔끔.**

---

## 방식 A(서버 전체 root)의 보안 문제점

핵심: **"인증 없는 원격 명령 실행 통로 + 최고 권한"의 결합.**

1. **인증 없는 `/api/exec` + root = 사실상 원격 root** *(가장 치명적)*
   - `_handle_exec`에 인증·토큰·세션이 전혀 없음.
   - 기본 바인딩 `WFSAT_HOST=0.0.0.0` → 같은 네트워크의 아무나 root 명령 실행 가능.

2. **서버의 어떤 버그도 곧 root 취약점**
   - 인증·TLS 없는 커스텀 HTTP 핸들러. 파싱 버그·경로 처리 실수·정적 파일 디렉터리 탈출 등이 전부 root로 악용됨. 권한 분리의 "피해 한정" 효과 소멸.

3. **`allow_args=True` 인자 주입 확대**
   - 명령 뒤에 임의 인자 부착 가능. `_FORBIDDEN_CHARS`가 셸 메타문자(`; | ` `` ` `` 등)는 막지만, 스크립트/도구가 인자를 해석하는 방식까지는 못 막음.
   - 예: `et_detector.py ... --json <임의경로>` 로 root 권한 임의 파일 쓰기/덮어쓰기 여지 → 무결성 훼손·DoS.

4. **CSRF / DNS 리바인딩** *(127.0.0.1로 바꿔도 남음)*
   - 인증 없는 상태변경 POST라, 브라우저로 악성 웹페이지를 여는 것만으로 `localhost:5000/api/exec`에 요청이 가 root 명령이 트리거될 수 있음.

5. **root 소유 파일/프로세스**
   - 로그·캡처·`detect.json`이 root 소유로 생성(캡처엔 자격증명 포함 가능).
   - 백그라운드 공격/AP가 `start_new_session`으로 root 데몬처럼 상주.

6. **평문 통신**
   - TLS 없음 → 명령·수집 데이터(자격증명 포함 가능)가 LAN에 평문으로 흐름.

## 로컬 전용 접속(호스트에서 VM 서버 접속)이면 안전한가?

**가장 위험한 문제(네트워크상 누구나 원격 root)는 거의 사라진다.** 단, "문제 없음"이 아니라 **"조건 충족 시 실습용으로 수용 가능"** 이 정확한 표현.

### 사라지는 위험
- **LAN 원격 장악 제거** — `0.0.0.0` 노출 문제 해소.
- **피해 반경이 VM 내부로 한정** — 진짜 격리된 VM이면 호스트 본체·실제 자산까지 번지지 않음. 스냅샷 롤백으로 복구 용이.

### 그래도 남는 위험
1. **CSRF / DNS 리바인딩 (가장 중요하게 남음)**
   - 호스트 브라우저로 접속하는 구조면, 그 브라우저로 악성 페이지를 여는 것만으로 VM 서버에 POST가 가 root 명령 트리거 가능.
   - → **VM 내부 브라우저**로만 접속하고, 그 브라우저로 실습 외 서핑을 안 하면 크게 줄어듦.
2. **VM 네트워크에 닿는 다른 주체**
   - 어댑터가 bridged/NAT 노출이면 여전히 외부에 열림 → **host-only(internal)** 로 두고 `127.0.0.1` 또는 해당 인터페이스에만 바인딩.
   - 같은 host-only 세그먼트의 다른 VM, 다중 사용자 호스트도 접근 가능.
3. **"격리" 전제가 실제로 지켜지는가**
   - **공유 폴더/클립보드/드래그앤드롭** 켜져 있으면 VM↔호스트 통로 생김(끄는 게 안전).
   - **실제 Wi-Fi 어댑터 패스스루** 시 VM이 주변 실제 네트워크를 공격 가능(운영·법적 리스크).
   - VM 탈출 취약점(확률 낮으나 0 아님).
4. **VM 내부 잔존 민감 데이터** — 탈취 자격증명·캡처가 root 소유로 남음. 실습 후 롤백/삭제.

### 결론
> **실제 Wi-Fi 미연결 / host-only 네트워크 / 공유기능 off / 일회용 격리 VM에서, VM 내부 브라우저로만 접속**한다면 → 잔여 위험 낮고 실습 목적으로 사실상 수용 가능.
>
> "로컬이니까 무조건 안전"이 아니라 **격리 전제가 지켜지는 한 안전.** 마지막으로 남는 건 **CSRF**이며, 최소 인증(커스텀 헤더/토큰)으로 거의 제거 가능.

## 완화 체크리스트

- [ ] `WFSAT_HOST=127.0.0.1` 로 바인딩 (또는 host-only 인터페이스 한정)
- [ ] VM 네트워크를 **host-only/internal** 로 설정, bridged/NAT 노출 금지
- [ ] VM **공유 폴더·클립보드·드래그앤드롭 비활성화**
- [ ] 가능하면 **VM 내부 브라우저**로만 대시보드 접속
- [ ] 안 쓸 땐 `WFSAT_ENABLE_EXEC=0` 으로 콘솔 비활성화
- [ ] `/api/exec`에 **최소 인증(공유 토큰 헤더)** 추가 → CSRF 방어
- [ ] 실습 전용 격리 네트워크 + 방화벽, 인터넷/사내망과 분리
- [ ] (권한 최소화) 서버는 일반 사용자로, root 필요한 도구만 `capabilities`(`cap_net_admin`, `cap_net_raw`) 또는 좁은 sudo 래퍼로 부여
- [ ] 실습 후 스냅샷 롤백/캡처 파일 삭제

## 환경 변수 참고

| 변수 | 기본값 | 설명 |
|------|--------|------|
| `WFSAT_HOST` | `0.0.0.0` | 바인딩 주소. 로컬 실습은 `127.0.0.1` 권장 |
| `WFSAT_PORT` | `5000` | 포트 |
| `WFSAT_ENABLE_EXEC` | `1` | `0`이면 명령 콘솔 비활성화 |
| `WFSAT_SUDO` | `sudo -n` | root 명령 앞에 붙일 sudo. `""`이면 자동 sudo 끔 |
| `WFSAT_EXEC_TIMEOUT` | `60` | 포그라운드 명령 타임아웃(초) |
| `WFSAT_LOG_DIR` | `/tmp/et_logs` | 백그라운드 실행 로그가 저장되는 디렉터리 |

> **실행/로그 방식**: `scan`·`attack`·`ap`·`deps`는 서버에서 **백그라운드**로 실행되어 브리지 터미널을 막지 않고, 출력은 `/tmp/et_logs/job_*.log`에 기록된다. 대시보드 콘솔이 이 로그를 폴링(`GET /api/exec/log`)해 **실시간으로 표시**하므로, 사용자는 서버 창을 볼 필요 없이 대시보드만 보면 된다. 조회성 명령(`config`·`iface`·`wifi`·`detect`)은 즉시 실행되어 결과가 콘솔에 바로 나온다.
